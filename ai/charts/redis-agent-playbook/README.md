# Redis Playbook Helm chart

This chart deploys the on-prem Playbook control plane and data plane. It
connects to a separately installed Iris Identity Service release (see
[Connecting to the Identity Service](#connecting-to-the-identity-service)) and
deploys none itself. It deliberately does not deploy Redis, issue TLS
certificates, generate license material, or create ingress resources. It can
lookup-generate the control-plane admin and internal tokens using the same
retained-Secret contract as the other Iris on-prem charts. Redis, license, certificate, and
ingress ownership remain platform decisions.

## Observability

Scrape `/metrics` on every CP and DP pod (default ports 9200 and 9201). Product API
and retrieval metrics use bounded operation/outcome labels for service health.
Structured application logs contain bounded operational errors. Playbook does
not emit per-entry usage records or provide a per-entry statistics API.

To send spans to a trusted local OTLP/gRPC collector:

```yaml
tracing:
  enabled: true
  otlpGRPCEndpoint: otel-collector.observability.svc:4317
  capture: none # set to received to include bounded query and returned content
```

Tracing and trace payload capture are off by default. Metrics follow existing
service wiring; the chart does not install a scraper, collector or analytics store.
The shared exporter uses plaintext to the local collector;
secure its upstream export separately. Existing shared HTTP spans may carry raw
paths, user agents and error descriptions, so apply collector redaction as needed.
Changing tracing enablement or endpoint rolls both Playbook roles when using
chart-rendered configuration; changing capture rolls only the data plane.
With `controlplane.config.existingSecret`, set the equivalent
`opentelemetry` configuration in that Secret and update its checksum instead.
The [instrumentation contract](../../docs/specs/MOD-19039-playbook-instrumentation.md)
defines signal shapes, capture limits, semantics, and collection guidance.

For calls through Context Gateway, configure Gateway and Playbook to export their
own spans to the same collector or backend. Gateway propagates its upstream
CLIENT span context in MCP `_meta`; Playbook emits the child SERVER span and the
backend joins them by trace ID. Gateway does not relay Playbook spans or baggage.
Cache hits and result-handle operations that do not reach Playbook have no
Playbook span. Each service's content-capture policy is independent. Playbook's
combined captured JSON/text values are limited to 64 KiB per serving span;
oversized values are omitted whole, with REST retaining document metadata when
content does not fit.

## Prerequisites

- Helm 3 and a Kubernetes cluster. Local validation uses KinD; a supported EKS
  and Kubernetes version matrix is not yet qualified.
- Two physically distinct Redis deployments. Metadata requires core Redis and
  Lua support; content requires RedisJSON plus RediSearch / Query Engine for
  JSON and vector indexes. The services reject aliased endpoints. The chart's
  KinD gate validates `redis:8` for both.
- Two explicitly tagged images: Playbook CP and Playbook DP.
- An `iris-identity-service` release (chart `0.10.0` or later) with the
  Playbook entries registered, and the data plane's runtime credential Secret
  (see [Connecting to the Identity Service](#connecting-to-the-identity-service)).
- A Playbook license Secret. The control-plane admin and internal tokens may be
  generated by the chart or supplied as distinct Secret/key references.
- An explicitly configured embedding model and its private client configuration.
- Network reachability; use authenticated, certificate-verified TLS for
  production dependencies, not only when enabling the FIPS profile.

The chart reads existing storage, license, inference, and optional CA Secrets.
For service credentials, a non-empty `existingSecret` takes precedence;
otherwise `autoGenerate: true` creates a random Secret with
`helm.sh/resource-policy: keep` and reuses its value through Helm's `lookup` on
upgrade. Set `autoGenerate: false` when platform policy requires BYO credentials.
Use existing Secrets for offline rendering or GitOps systems that do not perform
live Helm `lookup`; otherwise a fresh render can generate different credentials.

Start from
`examples/basic/prerequisites.example.yaml`, substitute values through your
secret manager, and never commit the rendered secrets. The storage Secret's
`playbook-storage.yaml` overlay supplies both `storage.metadata.urls` and
`storage.content.urls` to CP and DP. The Identity Service's metadata Redis
belongs to its own release (`metadata.*`); use a separate, least-privileged
Redis user even when it shares the physical metadata deployment.

Every existing-Secret reference has an optional checksum value. Set it to a
stable digest of the referenced Secret payload when the Secret name stays the
same across rotations. A changed checksum updates the pod template and rolls
only the workloads that consume that Secret:

```yaml
storage:
  existingSecretChecksum: "<sha256-of-storage-secret-data>"
license:
  existingSecretChecksum: "<sha256-of-license-secret-data>"
controlplane:
  adminToken:
    existingSecretChecksum: "<sha256-of-admin-token>"
```

The same contract is available for the inference Secret, private CA,
control-plane internal token, and the data plane's Identity Service credential. Store only the
digest in values, never the Secret material. If a Secret controller already
rolls consumers on rotation, these checksum fields may remain empty.

`inference.models` in Helm values accepts only the non-secret vector-space
identity (`provider`, `model`, and `dimensions`) and is rendered into a ConfigMap.
Do not place provider endpoints or credentials in values.

For a non-noop provider, set `inference.existingSecret` to a Secret whose
`inference.yaml` contains RAM-shaped `embedders_connection_details`:

```yaml
embedders_connection_details:
  private-embeddings:
    protocol: openai
    base_url: https://your-embedding-service.example/v1
    credentials:
      type: static
      api_key: REPLACE_PRIVATELY
    http_client:
      timeout: 30s
      max_retry_attempts: 3
    batching:
      embeddings:
        enabled: true
```

The public `inference.models` catalog lists immutable provider/model/dimensions
identities, and each provider selects a connection key such as
`private-embeddings`. Keep the catalog aligned between CP and DP. The CP receives
only that catalog; embedding endpoints and credentials are mounted only into the
DP. Unlike RAM on-prem's single deployment-wide embedding selection, Playbook
supports multiple immutable vector spaces selected when each Playbook is created;
there is no implicit default or per-binding embedding selection. A model or width
change requires a new Playbook; changing a connection must preserve its vector space.

Connection settings match RAM: `protocol` (defaults to the key), `base_url`,
`azure`, `credentials`, `http_client`, `embedding_input_max_chars`,
`embedding_input_fast_truncate`, and `batching.embeddings`. Canonical connections
use RAM's opt-in batching default; omitted enabled-batching limits use 10 items,
20ms wait, 10 workers, and a 1,000-item queue. The basic example explicitly enables
batching. `noop` is only a deterministic test provider.

## Install

These commands install from a repository checkout. First install the
[Identity Service release](#connecting-to-the-identity-service), provide loadable
images, create the prerequisite Secrets, and replace the example's placeholder
image tags and credentials.

```bash
helm repo add redis-ai https://helm.redis.io/ai --force-update
helm dependency build playbook/helm
helm lint playbook/helm -f playbook/helm/examples/basic/values.yaml
helm upgrade --install playbook playbook/helm \
  --namespace redis-ai --create-namespace \
  -f playbook/helm/examples/basic/values.yaml \
  --set tests.enabled=true
helm test playbook --namespace redis-ai
```

The chart pins the published `redis-iris-onprem-lib` 0.3.0 from
`https://helm.redis.io/ai`. Run `helm dependency build playbook/helm` before
linting, rendering, or local installation. Dependency resolution also works
when the package workflow copies the chart outside this repository.

Install-time validation requires non-empty image tags, tenant, storage and
license Secret references, an explicit model list, the Identity Service URL and
data-plane credential, plus either a generated or existing Secret for each
control-plane token. It refuses to mount the same Secret key as two credential
roles. Operators must keep all resolved credential values distinct, even with
differently named Secrets.

Services default to ClusterIP:

- CP on `9200`, for approved administrators and Identity Service grant validation.
- DP on `9201`, for public REST and streamable-HTTP MCP callers.

## Connecting to the Identity Service

The **Iris Identity Service (IdS)** mints Playbook agent keys, answers the data
plane's introspection calls and, with `extraction.connection`, holds the
extraction workers' subject grants. This chart deploys none: install the
[`iris-identity-service`](../../identity-service/helm/README.md) chart as its
own release, then connect this release to it. The minimum Identity Service
chart version validated with this chart is `0.10.0`.

Neither chart reads the other's values or checks them against its own. Keeping
the two releases consistent is the deployment automation's job. The end-to-end
KinD harness proves that a consistent pair works; `helm test` does not.

### Two-step install

The tested layout puts both releases in one namespace, because both mount the
shared Secrets. With the Secrets from
[`examples/basic/prerequisites.example.yaml`](examples/basic/prerequisites.example.yaml)
and the Identity Service metadata Secret in place:

1. Install the Identity Service release with the Playbook entries from
   [Product contracts](#product-contracts):

   ```bash
   helm install iris-identity-service redis-ai/iris-identity-service \
     --namespace redis-ai -f values-ids.yaml
   ```

2. Install this chart with the connection values:

   ```yaml
   tenantId: default
   dataplane:
     identityServiceBaseURL: http://iris-identity-service:9200
   identityService:
     # The in-cluster Service speaks http; refused under fips.
     allowInsecureTransport: true
     credential:
       existingSecret: playbook-dp-credential
   controlplane:
     internalToken:
       existingSecret: playbook-controlplane-internal
   ```

[`examples/basic/values.yaml`](examples/basic/values.yaml) is a complete values
file for this layout.

### Connection values

| Key | Default | Purpose |
| --- | --- | --- |
| `dataplane.identityServiceBaseURL` | `""` | The Identity Service release's URL. The data plane introspects agent keys and looks up worker grants there; the extraction connection's source and destination Identity Service URLs default to it. Required. Must be `https://` unless `identityService.allowInsecureTransport=true`. |
| `identityService.allowInsecureTransport` | `false` | Accept an `http://` Identity Service URL, for example the in-cluster Service. Refused under the fips profile. |
| `identityService.credential.existingSecret` | `""` | The data plane's runtime credential (`playbook-dp`), mounted at `/etc/identity-service/runtime/playbook-dp/token`. Required. |
| `identityService.credential.secretKey` | `token` | Key in that Secret. |
| `identityService.credential.existingSecretChecksum` | `""` | Set to roll the data plane when the Secret's content changes. |
| `controlplane.internalToken.existingSecret` | `""` | The control plane's internal token, which the Identity Service release presents to the grant validator. |

The Playbook data plane always authenticates agent keys, so the URL and
credential are required in every configuration. The data-plane config is fully
chart-rendered; there is no introspection block to set by hand.

`identityService.*` no longer holds Identity Service values: the schema rejects
any key other than `allowInsecureTransport` and `credential`, and rejects
`storage.identityServiceKey`.

### Secret ownership

A Secret that both releases mount is owned by deployment automation and
reaches each chart as `existingSecret` + `secretKey`.

| Secret | Who owns it | Playbook value | Identity Service value |
| --- | --- | --- | --- |
| Data-plane runtime credential (`playbook-dp`) | Deployment automation | `identityService.credential.existingSecret` | `runtime.serviceCredentials[].existingSecret` |
| Control-plane internal token | Deployment automation (this chart generates `<fullname>-controlplane-internal-token` in development only) | `controlplane.internalToken.existingSecret` | `productValidation.products.playbook.credential.existingSecret` |
| Control-plane admin token | Deployment automation, or this chart | `controlplane.adminToken.existingSecret` | None |
| Identity Service metadata Redis config | You | None | `metadata.existingSecret` |
| Identity Service Control token | The Identity Service release, or you | None | `control.*` |

Keep every token distinct: the internal token must not reuse the admin token,
and the chart refuses to mount one Secret key as two of its credentials. It
cannot compare values held in differently named Secrets.

### Product contracts

This mirrors "Product contracts" in the
[Identity Service chart README](../../identity-service/helm/README.md#product-contracts).
The addresses assume this chart installed as release `playbook` (fullname
`playbook-redis-agent-playbook`) and an Identity Service release named
`iris-identity-service`. After changing either, `fullnameOverride`, or a Service
port, restate them on both releases.

| Set on this release | Value | Matching Identity Service value |
| --- | --- | --- |
| `dataplane.identityServiceBaseURL` | `http://iris-identity-service:9200` (the release's Service on its `service.port`, default `9200`) | None |
| `identityService.credential.existingSecret` + `secretKey` | The data plane's runtime credential | `runtime.serviceCredentials[]` entry `name: playbook-dp`, `subject: playbook-dp`, `allowedOperations: [api-key-introspect]` (plus `subject-grant-lookup` with `extraction.connection.enabled`), `allowedProducts: [playbook]`, the same `existingSecret` + `secretKey` |
| `controlplane.internalToken.existingSecret` + `secretKey` | The control plane's internal token | `productValidation.products.playbook.credential` |
| `controlplane.service.port` | `9200` | `productValidation.products.playbook.baseURL`: `http://playbook-redis-agent-playbook-controlplane:9200` |
| `tenantId` | `default` | `runtime.apiKeyTenant.singleTenantID` |
| `extraction.connection.enabled` | `true` | `subjectGrants.allowed` entry `{product: playbook, resourceType: playbook, actions: [read, propose]}` |
| `extraction.connection.destinationControlAudience` | `api://playbook-identity-control` | `controlAuth.workloadIdentity` trusts `system:serviceaccount:<namespace>:playbook-redis-agent-playbook-controlplane` with `roles: [subject_grant_admin]` and this audience |

The matching Identity Service values, without extraction:

```yaml
runtime:
  apiKeyTenant:
    singleTenantID: default
  serviceCredentials:
    - name: playbook-dp
      subject: playbook-dp
      allowedOperations: [api-key-introspect]
      allowedProducts: [playbook]
      existingSecret: playbook-dp-credential
      secretKey: token
productValidation:
  products:
    playbook:
      baseURL: http://playbook-redis-agent-playbook-controlplane:9200
      credential:
        existingSecret: playbook-controlplane-internal
        secretKey: token
```

The Identity Service asks the control plane to validate every grant before it
persists a key, at `/internal/v1/grants/validate`, presenting the internal
token. With chart-rendered configuration the control plane always reads that
token from its mounted file; with `controlplane.config.existingSecret`, include
`auth.internal_token.token_file` in your config Secret.

Every agent key carries a tenant. Set the Identity Service release's
`runtime.apiKeyTenant.singleTenantID` to this chart's `tenantId`; the control
plane also requests every extraction grant in `tenantId`. Neither chart can
check that the two values match. If the same release serves Agent Memory, both
products use one tenant, and Memory's `runtime.unscopedGrantsProduct: memory`
stays; Playbook needs no unscoped-grants product.

For extraction, one Identity Service release can serve both Agent Memory and
Playbook. It then carries both products' entries, `subject-grant-lookup` on
both data-plane credentials, both `subjectGrants.allowed` entries
(`memory/mem-store [read]` and `playbook/playbook [read, propose]`), and one
`controlAuth.workloadIdentity` subject for this control plane with
`audience: [api://memory-identity-control, api://playbook-identity-control]`.
See [Deploy and enable the extraction stack](#deploy-and-enable-the-extraction-stack).

### Cross-namespace

The Identity Service release can run in another namespace. Then:

- point `dataplane.identityServiceBaseURL` at its fully qualified Service, for example
  `http://iris-identity-service.<identity-service-namespace>.svc:9200`;
- set its `productValidation.products.playbook.baseURL` to
  `http://playbook-redis-agent-playbook-controlplane.<namespace>.svc:9200`;
- provision both shared Secrets with the same values in both namespaces, since
  a Pod mounts Secrets only from its own namespace;
- allow the Identity Service pods to reach the control plane on port `9200`
  and the data plane and control plane to reach the Identity Service (see
  [`networkpolicy.reference.yaml`](networkpolicy.reference.yaml)).

The KinD harness tests the same-namespace layout only.

### Global fallbacks

`global.security.profile`, `global.imagePullSecrets` and
`global.tls.caCertSecret` are read when this chart's own `security.profile`,
`imagePullSecrets` or `tls.caCertSecret` is empty, matching the Identity Service
chart, so an umbrella chart's single `global` block configures both releases. A
local value wins.

### FIPS and TLS trust

Under the fips profile the Identity Service hop must be TLS, with no opt-out:
every Identity Service URL must be `https://` and the chart refuses
`identityService.allowInsecureTransport=true`. Neither chart terminates TLS; put
a mesh, gateway or TLS-terminating proxy in front of the Identity Service. The
data plane and control plane trust `tls.caCertSecret` (or
`global.tls.caCertSecret`) for that URL, on top of the system CAs.

The validator hop is configured on the Identity Service release: under fips its
`productValidation.products.playbook.baseURL` must be an `https://` control-plane
endpoint, trusted through that release's own `tls.caCertSecret`. Set
`security.profile` (or `global.security.profile`) on both releases.

### Upgrading from `0.1.x`

`helm upgrade` from a `0.1.x` chart, which bundled the Identity Service, is
unsupported. The following manual migration is untested guidance:

1. Preserve the control plane's internal token. A chart-generated one lives in
   `<fullname>-controlplane-internal-token`, key `token`. The data plane's
   runtime credential becomes a new `playbook-dp` Secret; you can reuse the
   value of the generated `<fullname>-identity-service-runtime-token`.
2. Hand both values to deployment automation, which creates the shared Secrets.
3. Install the Identity Service release with those Secrets registered as in
   [Product contracts](#product-contracts), pointing `metadata.existingSecret`
   at the metadata Redis and key namespace the bundled service used (the old
   `storage.identityServiceKey` overlay), so existing agent keys and grants keep
   working.
4. Uninstall the `0.1.x` release, delete the bundled Identity Service Secrets
   Helm keeps (`<fullname>-identity-service-*`), and install this chart with the
   connection values. Remove every old `identityService.*` key and
   `storage.identityServiceKey` from your values; the schema rejects them.
5. Keep the tenant your existing Playbooks and keys use: set `tenantId` and the
   Identity Service release's `runtime.apiKeyTenant.singleTenantID` to it.

## MCP endpoint exposure

The existing DP Service on port `9201` serves both REST and the first-class MCP
URL `/v1/playbooks/{playbookId}/mcp`. There is no separate MCP workload, Service,
port, or enable flag. The chart creates no ingress: expose this path through your
platform's TLS ingress/gateway and retain the complete path, bearer Authorization
header, request body, and MCP/Accept headers. Route it to the data-plane Service,
using POST for MCP messages. Authenticated GET/DELETE return 405 because the
transport is stateless; a successful browser GET is not an MCP readiness check.

Find the chart's DP Service using its release labels:

```bash
kubectl -n redis-ai get services \
  -l app.kubernetes.io/instance=playbook,app.kubernetes.io/component=dataplane
kubectl -n redis-ai port-forward --address 127.0.0.1 \
  service/<dataplane-service> 9201:9201
```

For this local tunnel, configure a standard MCP client with
`http://127.0.0.1:9201/v1/playbooks/<playbook-id>/mcp` and a read-scoped Playbook
agent key. Use the platform HTTPS origin for remote callers. See the
[client configuration and retrieval flow](../README.md#connect-an-mcp-client).

`task playbook:test:onprem-kind` (an alias of
`task test:identity:integration FLOW=playbook`; see
[the KinD harness](../../tests/kind/README.md)) runs the standard Go MCP SDK through this
Service port-forward. The check
initializes, lists the three read-only tools, discovers a published Skill, loads
the selected version despite a newer draft, fetches files through both MCP
surfaces, checks missing/invalid/read-denied credentials and stateless methods,
and rejects stale pins/URIs after publication changes. It creates a temporary
Playbook and revokes its keys/deletes the Playbook afterward.

To run just that check against a disposable deployment configured with a `noop`
test model, first generate the Playbook and Identity Service bindings. Set
`PLAYBOOK_CP_URL`, `PLAYBOOK_DP_URL`, and `PLAYBOOK_IDS_URL` plus
`PLAYBOOK_ADMIN_TOKEN` and `PLAYBOOK_IDS_CONTROL_TOKEN` through your environment.
The CP and IdS Control URLs may be separate private port-forwards:

```bash
PLAYBOOK_MCP_DEPLOYMENT_TEST=1 \
PLAYBOOK_MCP_MODEL=playbook-local PLAYBOOK_MCP_DIMENSIONS=384 \
  go test -tags=integration ./playbook/tests/integration/onprem \
    -run '^TestDeployedMCP$' -count=1 -timeout=3m
```

Use the model name/dimensions configured in that deployment. The same contract
runs locally against real Redis and Identity Service with:

```bash
go test -tags=integration -race -cover ./playbook/tests/integration/onprem \
  -run '^TestLifecycleSuite$/^TestMCPReadOnlyEndpoint$' -count=1 -timeout=5m
```

These checks provide repeatable Service/protocol coverage. A deployment's public
TLS ingress, certificate trust, and chosen client configuration still need to be
verified against its actual origin; repository tests do not qualify an external
production ingress.

## Browser UI routes and operator authentication

See the [direct browser access contract](../../docs/specs/MOD-18530-playbook-direct-browser-access.md)
for the complete CP/DP split and admin policy.

Configure the UI gateway with a visible `playbook` route to CP port `9200` and
a hidden `playbook-dp` route to DP port `9201` (see `iris/ui/helm/values.yaml`). The
browser sends inventory and settings to `/api/playbook/*`; entries, revisions,
proposals, resources, and Discovery go to `/api/playbook-dp/*`. Both paths stay
on the UI origin and forward the caller's bearer token. CP does not proxy DP
content. The gateway accepts a CA Secret for each HTTPS upstream; the ingress
serving the browser must terminate TLS separately.

The default CP admin token remains available and the Identity Service release
serves agent keys. To enable browser OIDC administration, configure `dataplane.oidc`
with the issuer, JWKS URI, tenant source, and trusted human group-to-role
mappings. Then set `controlplane.oidc.enabled=true`. The control plane uses
`auth.oidc.audience` (see "Token audience" below), the same value as the data
plane. The control plane validates
operator tokens locally against the same issuer, JWKS, tenant source, and group
mappings, with the shared authenticator the data plane uses. It never calls the
Identity Service for this, so there is no extra credential, Secret, or network
route to configure. A configured static OIDC tenant must equal `tenantId`.
Allow control-plane egress to the JWKS endpoint (see
`networkpolicy.reference.yaml`). If you supply a full control-plane config
Secret, include the matching `auth.oidc` block yourself; see
`docs/specs/MOD-17647-unified-onprem-infrastructure.md` for its shape.

Upgrading from `controlplane.delegatedAuth`: the chart refuses that block. Move
its `enabled` to `controlplane.oidc` and drop the rest; the audience comes from
`auth.oidc.audience`, and a leftover `controlplane.oidc.audience` fails the render. The
previously generated `-auth-introspect` Secret is kept by Helm's resource policy
and is no longer used; delete it once the upgrade is done.

The UI stores one access token and sends it to every backend, so the control
plane and data plane accept one shared audience (see "Token audience" below).
Validate a real operator token against both services before rollout. Explicitly
mapped human `product_admin` and `suite_admin` roles receive tenant-wide
`playbook:*` full access at DP after its tenant check. New Playbooks are usable
immediately. This MVP policy needs Teo's approval. Nonadmin human grants
remain MOD-18385 work. The UI currently accepts a pasted access token.

Keep CP administration and IdS Control routes private; exposing an entire IdS
Service also exposes its administrative routes. Use the platform ingress or
gateway to expose only approved routes. Adapt
`networkpolicy.reference.yaml` after resolving every placeholder; do not apply
it verbatim. Include Redis, DNS, and inference-provider egress. Standard NetworkPolicy
does not express provider FQDN allowlists; use approved IP ranges or an egress proxy.

## Federated data-plane authentication

The data plane can validate corporate IdP access tokens directly while keeping
Identity Service agent keys enabled for callers without a corporate identity.
This preview is disabled by default. Enable it with the IdP issuer and JWKS
endpoint, plus either a claim that identifies the Playbook tenant or a fixed
tenant for a single-tenant installation. Set exactly one of `tenantIDClaim`
and `staticTenantID`; chart validation rejects configurations that set both:

```yaml
tenantId: customer-tenant
dataplane:
  oidc:
    enabled: true
    issuer: https://idp.example.com/tenant
    jwksURI: https://idp.example.com/tenant/keys
    tenantIDClaim: tid
    roleClaims:
      - groups
    roleMappings:
      playbook-admins: product_admin
      suite-admins: suite_admin
```

The accepted audience is `auth.oidc.audience`, described below. The chart does
not expose an `azp` fallback. The resolved tenant must equal the
chart's `tenantId`, even for suite admins. For an issuer without a tenant claim,
use `staticTenantID` equal to `tenantId` only when that issuer and its admin
groups are confined to this deployment's tenant. A shared multi-tenant issuer
must use `tenantIDClaim` to preserve that boundary.

`roleMappings` defaults to `{}`; unmapped claims never grant access, even if
their values spell an Iris admin role. Map only trusted human-admin groups.
Agent keys and worker identities keep their explicit resource grants. OIDC
tokens from services must not be assigned these human-admin groups.

### Token audience

> **Upgrading with `dataplane.oidc.enabled`.** The default audience is
> `api://redis-iris`; the data plane used to accept only `api://playbook-dp`. To keep
> accepting tokens issued for it, set `auth.oidc.audience: api://playbook-dp` before
> upgrading. `controlplane.oidc.audience` no longer exists: the control plane uses
> `auth.oidc.audience`, and the render fails if it is still set.
> `extraction.connection` keeps its own fixed `api://playbook-dp` audience for the
> worker token.

`auth.oidc.audience` is the audience the IdP puts in the access token's `aud`,
set next to the issuer and claim settings above. It defaults to
`api://redis-iris`, the single Iris API audience shared by every Iris service
that validates IdP tokens, and it is the value the data plane accepts. The
control plane uses the same single value, so the two cannot diverge. A token is accepted when its `aud` (a string or a list)
contains the configured value, and rejected otherwise.

| IdP | `auth.oidc.audience` |
|---|---|
| Okta, Auth0, Keycloak, PingFederate, AD FS | the audience or API identifier you configured, for example `api://redis-iris` |
| Entra ID, v2 tokens | the API's Application (client) ID GUID |
| Entra ID, v1 tokens | the Application ID URI, for example `api://redis-iris` |

Use the same value in every Iris chart (the UI sign-in setting for it arrives with MOD-19450). If you
supply your own data-plane or control-plane config Secret, set the audience in
its `auth.oidc` block yourself. The chart refuses an empty or wildcard value, and warns
in the release notes when the value differs from the default.

Allow data-plane egress to the configured JWKS endpoint. Verification uses a
cached key set: a refresh outage returns a temporary service failure when no
usable cached key can validate the token, rather than treating the token as bad
credentials. The chart currently uses the fixed shared defaults: a 10-minute
JWKS cache TTL, 5-minute clock skew, and 30-second JWKS HTTP timeout. A signed
token normally remains usable through its expiration. Account for these fixed
defaults when setting token lifetimes and retiring an issuer key.

HTTP issuer or JWKS URLs require the explicit
`allowInsecureTransport: true` development opt-in. The FIPS profile rejects
that opt-in and requires HTTPS for both endpoints. Mount private CA material
through `tls.caCertSecret` when the IdP uses an internal certificate authority.

## Reading Agent Memory for extraction (MOD-19110)

For an installation from scratch, follow the
[deployment walkthrough](#deploy-and-enable-the-extraction-stack) below. It covers
both charts, the worker's separate credentials, and binding activation.

`extraction.connection` connects extraction bindings to a Redis Agent Memory
(RAM) installation. The control plane uses the isolated Identity Service Control
credential to grant `workerSubjects` read on each bound store. Identity Service
asks RAM to validate store existence and ownership by the grant tenant before
persisting a grant. The control
plane has no RAM data-plane credential or route; workers validate live access with
their own projected tokens during extraction. Deleting the last binding to a store
withdraws the shared grants. See the
[extraction ADR](../../docs/adr/MOD-18196-playbook-memory-extraction.md).

```yaml
extraction:
  enabled: true
  connection:
    enabled: true
    issuer: https://kubernetes.default.svc.cluster.local   # this cluster's ServiceAccount issuer
    jwksURI: https://kubernetes.default.svc.cluster.local/openid/v1/jwks
    # Optional: defaults to dataplane.identityServiceBaseURL. Set it only when
    # RAM uses a different Identity Service release.
    # identityServiceBaseURL: https://ram-identity-service:9200
    # Optional: the control plane's URL for the data plane's Identity Service
    # release (destination grants); defaults to dataplane.identityServiceBaseURL.
    # destinationIdentityServiceBaseURL: https://identity-service.example:9200
    workerSubjects:
      - system:serviceaccount:<namespace>:<worker-serviceaccount>
```

The control plane does not hold an Identity Service Control token. It gets its
own ServiceAccount, `<fullname>-controlplane`, and provisions grants with
projected ServiceAccount JWTs: audience `sourceControlAudience` for the
Identity Service RAM uses and `destinationControlAudience` for the control
plane's Identity Service. Usually one release serves both and lists both
audiences. Each Identity Service release trusts the subject
`system:serviceaccount:<namespace>:<fullname>-controlplane` with the role
`subject_grant_admin`. That role permits only subject-grant operations, in
`tenantId`.

On the Identity Service release, set `controlAuth.workloadIdentity` with this
cluster's issuer and JWKS, the audiences `sourceControlAudience` and
`destinationControlAudience`, and that subject with
`roles: [subject_grant_admin]` (on separate releases, each gets its own
audience). The Control tokens stay valid as rescue credentials, and only the
Identity Service pods mount them. This chart no
longer has the `controlToken` and `destinationControlToken` values. If you set
them, rendering fails.

An existing `0.1.x` install cannot be upgraded in place; see
[Upgrading from `0.1.x`](#upgrading-from-01x).

The subject's tenant
in RAM must be this chart's `tenantId`, because the control plane requests every
grant in that tenant.

On the RAM side, list the same
subjects under `memory.auth.service_subjects` with this issuer, its JWKS, and
audience `api://memory-dp`, and add `subject-grant-lookup` to the RAM data
plane's runtime credential on that Identity Service release. On that release,
also configure `subjectGrants.allowed` with `product: memory`,
`resourceType: mem-store`, and `actions: [read, read_all_owners]`; its empty
default denies all subject grants (see the Identity Service chart README,
"Product contracts"). The control plane requests both actions.
`read_all_owners` lets the worker read the sessions of all owners in the store
when RAM enforces ownership. Upgrade that Identity Service release and the RAM
chart first: they bring the Identity Service and control plane images that know
`read_all_owners`, and the wider allowed list.
If RAM refuses the full grant, the control plane falls back to `read` and logs
a warning. Then the worker cannot read personal sessions when RAM enforces
ownership. The next reconcile after you widen the list installs the full grant. See the [RAM service-subject example](../../memory/helm/README.md#service-subject-authentication-playbook-extraction-mod-19110).
The Playbook tenant must own the
RAM store. RAM validates ownership during grant preparation and rechecks it when
the worker reads. A foreign-tenant store blocks preparation as `source_grant_refused`.

The RAM data plane must be able to fetch the issuer's JWKS. On a cluster whose
ServiceAccount issuer is a public OIDC endpoint (for example EKS), no extra
setup is needed. Otherwise RAM needs the cluster CA (`tls.caCertSecret`) and
unauthenticated access to the issuer discovery documents, because the shared
JWKS client sends no credential. `tests/integration/identity/kind/playbook-ram-e2e.sh`
shows the complete setup on KinD.

### Destination preparation and authentication

When `extraction.connection.enabled=true`, Playbook DP accepts the configured
issuer/subjects with audience `api://playbook-dp` and looks up their grants on
`dataplane.identityServiceBaseURL`. The CP provisions destination grants on
`extraction.connection.destinationIdentityServiceBaseURL`, which defaults to the
same URL. Set it only when the control plane reaches the Identity Service at a
different URL than the data plane (for example on Neptune); runtime lookup and
CP mutation must still reach one authority. That
release must carry the `playbook/playbook [read, propose]` subject-grant policy,
`subject-grant-lookup` on the `playbook-dp` credential, and workload trust for
the control-plane subject with the audience `destinationControlAudience`, the
tenant `tenantId` and the role `subject_grant_admin` (see
[Product contracts](#product-contracts)).

The CP's `allow_insecure_transport` covers its source and destination Identity
Service and RAM CP calls. It is on when `extraction.connection.allowInsecureTransport`
or `identityService.allowInsecureTransport` is set; an `http://` source URL needs
`identityService.allowInsecureTransport`. FIPS refuses both.

Issuer and JWKS must use HTTPS unless insecure transport is explicitly allowed;
FIPS requires HTTPS. Both data planes must trust the issuer CA and reach JWKS.
Roll updated IdS readers to all replicas before enabling this capability. Durable
management metadata makes old IdS rollback unsupported while it remains present.
Destination cleanup preserves borrowed grants and administrator replacements.
A retired binding management identity cannot be reused at the same subject/resource;
reintroduce a retired worker with a new binding or separately administered access.

### Operator flow for the bindings API

1. Deploy the Identity Service release RAM connects to, then RAM CP and RAM DP,
   with the service-subject configuration above (RAM deploys no Identity
   Service of its own). Create the source store through RAM CP under the same
   tenant as the Playbook. Choose a tenant-specific worker ServiceAccount subject;
   configure its grants and deploy the [extraction worker](#extraction-worker).
2. Deploy Playbook CP and DP connected to that Identity Service release, with
   metadata/content Redis and the usual Playbook storage, auth and inference
   configuration. Do not copy the Identity Service Control token. The control plane uses its own ServiceAccount JWT.
   The `controlAuth.workloadIdentity` of the Identity Service release RAM uses must trust its subject
   before you enable the connection. Set `extraction.enabled: true` and
   `extraction.connection.enabled: true` as shown above, with the exact worker
   subjects (the source endpoint defaults to `dataplane.identityServiceBaseURL`). Roll every CP replica to the same configuration.
3. Allow Playbook CP → Identity Service Control, Playbook DP → Identity Service
   Runtime, and Identity Service → RAM CP and Playbook CP validation.
   The [Playbook network-policy reference](networkpolicy.reference.yaml) supplies
   the egress rule and the [RAM reference](../../memory/helm/networkpolicy.reference.yaml)
   supplies the corresponding ingress rules. Replace namespaces, release labels,
   TLS gateway selectors and ports for your deployment. CP reaches Playbook
   metadata/content Redis directly for lifecycle/index administration; this flow
   adds no CP → Playbook DP or CP → RAM DP HTTP call.
4. Create a Playbook through Playbook CP, then POST its
   `/v1/playbooks/{playbookId}/extraction/bindings` with
   `source: {type: redis_agent_memory, storeId: ...}` and `job: {type: faq}`.
   Poll GET until `ready`, then PATCH `enabled: true` with the current
   `expectedVersion`. One binding per Playbook is supported. `ready` proves store
   existence, tenant ownership validation and accepted source/destination grants; it does not prove
   worker connectivity or model configuration. Configure the worker's destination and
   model credentials as described in the [worker setup](#extraction-worker).

To stop the capability, set `extraction.enabled: false` and retain
`extraction.connection.enabled: true`, the endpoint and RAM's workload trust.
Inspection, pause, deletion and grant reconciliation still work; creation,
resume and policy edits return `ExtractionDisabled` (409). Pause retains grants.
Delete bindings and wait for GET to return 404 before disabling the connection
or removing RAM's workload trust. Failed/unavailable cleanup leaves disabled deleting
records for retry. With `controlplane.config.existingSecret`, supply both settings
in that config and update `existingSecretChecksum` to trigger the CP rollout.

When retiring a worker, pause affected bindings and stop that workload. Remove
its subject from `extraction.connection.workerSubjects` and finish the control
plane rollout. Reconciliation of preparing/ready bindings revokes retired identities
recorded in its durable tenant/store grant journal; deleting the last binding
also revokes all recorded identities. Delete/recreate blocked bindings to retire
their identities. Failed cleanup retains ownership history
for retry. Verify current-worker access and retired-worker denial after RAM's
hard cache TTL before resuming. Remove the retired subject from RAM's allowlist
as well. Old replicas can regrant their configured subjects during a rollout.

The journal tracks grants this deployment attempts to install. It cannot discover
historical or other deployments' grants. Changing the source Identity Service
URL (`extraction.connection.identityServiceBaseURL`, or `dataplane.identityServiceBaseURL`
while that is empty) fails closed for stores with recorded grants at the old authority. While CP still points
to that authority, delete all affected bindings and wait for removal; confirmed
cleanup clears their journal. Then switch endpoints and recreate bindings. Restore
the old endpoint configuration first if the migration was started prematurely.
Preserve metadata Redis
and its grant journal when moving or restoring this deployment.

RAM caches grants separately for each service subject. The worker retries HTTP
403 responses for up to six minutes before blocking and pausing the binding;
no extraction or proposal write runs while access is denied. This covers the
default five-minute hard cache TTL. Keep RAM's hard cache TTL below that grace
period. Invalid identity (401) blocks immediately. Cross-scope source data is
rejected as `invalid_source` without disabling a healthy binding.


## Deploy and enable the extraction stack

This walkthrough installs from a checkout containing MOD-18529. Use images built
from that revision; enabling values on an older image does not add extraction.
It uses namespace `redis-ai`, RAM release `redis-agent-memory`, and Playbook
release `playbook`, without name overrides. The resulting worker subject is
`system:serviceaccount:redis-ai:playbook-redis-agent-playbook-worker`. Adjust that
subject everywhere if you change the namespace or chart resource names.

### 1. Prepare storage, images, Secrets and network access

Prepare `ram-values.yaml` using the [RAM chart installation guide](../../memory/helm/README.md)
and `playbook-values.yaml` using this chart's [prerequisites](#prerequisites) and
[basic example](examples/basic/values.yaml). Replace all example image tags,
license material, storage references and embedding configuration. This walkthrough
uses RAM's admin-token store creation, which assigns RAM's `tenantId` (for example
`default`). Set Playbook `tenantId: default` and `TENANT_ID=default` to match the source
and destination tenant.
If you reuse a store, verify its actual tenant before choosing the Playbook tenant.

The complete stack consists of one Identity Service release shared by both
products, RAM CP/DP, Playbook CP/DP, the Playbook extraction worker, and their Redis
dependencies. Provision a persistent regional queue Redis in addition to the
physically distinct Playbook metadata and content Redis deployments. Configure
RAM storage through its own chart. RAM's promotion worker is not required for
Playbook to extract from session events; its promotion/model settings are
independent of the Playbook extraction model.

This branch fixes RAM's promotion-worker health-server auth registration so it
can start with the shared agent-key/service-subject configuration. Build the RAM
image from this revision too; an older image can still fail with a missing
`PrincipalAuthenticator` at worker startup. Keep agent-key/service-subject auth
enabled on RAM DP. Stopping RAM's worker is not required to enable extraction. RAM
background jobs also need a callback URL and their own authenticated worker
identity. The overlay below supplies the projected token and matching callback
settings; see [RAM worker service-account authentication](../../memory/helm/README.md#worker-service-account-authentication).
`workerAuth` mounts the token; it does not configure the callback or grant access
by itself. RAM's `redis-agent-memory` worker audience and write grants are
separate from Playbook's `api://memory-dp` read-only service-subject grants.

Create prerequisite Secrets in the namespace before installing. Configure
verified TLS endpoints through your platform's mesh, gateway or ingress; neither
chart provisions API TLS termination. The HTTPS names below are placeholders for
those endpoints, not services the charts create. Configure the issuer and its
JWKS URI for your cluster, and verify RAM can fetch JWKS without a bearer token.
Mount private CA material with `tls.caCertSecret` where needed. Apply the
[network policies](#operator-flow-for-the-bindings-api), including worker access
to RAM DP, Playbook DP, queue Redis and the model provider.

The issuer must exactly match RAM's accepted issuer. `sourceURL` is RAM DP and

helm upgrade --install playbook playbook/helm --namespace redis-ai \

### 4. Create a source store and Playbook

Use approved API endpoints or local port forwards. In the commands below,
`RAM_CP_URL`, `PLAYBOOK_CP_URL` and `PLAYBOOK_IDS_URL` identify those endpoints;
`RAM_ADMIN`, `PLAYBOOK_ADMIN` and `PLAYBOOK_IDS_CONTROL` come from the corresponding
operator credentials, loaded privately. `TENANT_ID` must match the configured
tenant. These requests require `curl` and `jq`. Keep response files private:

```bash
umask 077
TENANT_ID=default
curl --fail-with-body -sS -X POST "$RAM_CP_URL/v1/stores" \
  -H "Authorization: Bearer $RAM_ADMIN" -H 'Content-Type: application/json' \
  --data '{"name":"playbook-source"}' --output ram-store.json
STORE_ID=$(jq -r '.storeId' ram-store.json)

curl --fail-with-body -sS -X POST "$PLAYBOOK_CP_URL/v1/playbooks" \
  -H "Authorization: Bearer $PLAYBOOK_ADMIN" -H 'Content-Type: application/json' \
  --data '{"name":"extracted-faqs","embedding":{"provider":"openai","model":"text-embedding-3-small","dimensions":1536}}' \
  --output playbook.json
PLAYBOOK_ID=$(jq -r '.playbookId' playbook.json)

```

Replace the Playbook embedding identity above with an entry in your configured
`inference.models` catalog, or reuse an existing Playbook and source store. The
connected chart projects distinct RAM and Playbook worker tokens. Binding
preparation provisions destination read/propose access automatically. Do not add
`worker.target_token` to that Secret; it conflicts with the chart's
`worker.target_token_file`. Legacy manually configured workers may use either a
static target token or a target token file, with their separately administered
read/propose grants; CP does not modify those keys.

Fill in the overlay's queue Redis URL, generation provider endpoint, model and
model API credential as well. Save that private file as `worker.yaml`, then
create the Secret without placing its payload in Helm values:

```bash
kubectl --namespace redis-ai create secret generic extraction-worker \
  --from-file=worker.yaml=worker.yaml
```

RAM source authentication uses the worker's
projected ServiceAccount token automatically; do not substitute a destination token
or the Identity Service Control credential for it.

### 5. Prepare the binding, start the worker, then activate

Create a binding; it starts disabled:

```bash
jq -n --arg store "$STORE_ID" \
  '{source:{type:"redis_agent_memory",storeId:$store},job:{type:"faq"}}' \
  > binding-request.json
curl --fail-with-body -sS -X POST \
  "$PLAYBOOK_CP_URL/v1/playbooks/$PLAYBOOK_ID/extraction/bindings" \
  -H "Authorization: Bearer $PLAYBOOK_ADMIN" -H 'Content-Type: application/json' \
  --data-binary @binding-request.json --output binding.json
BINDING_ID=$(jq -r '.bindingId' binding.json)

curl --fail-with-body -sS \
  "$PLAYBOOK_CP_URL/v1/playbooks/$PLAYBOOK_ID/extraction/bindings/$BINDING_ID" \
  -H "Authorization: Bearer $PLAYBOOK_ADMIN" --output binding.json
```

Repeat GET until `status` is `ready`; investigate `blocked` rather than activating
it. Preparation validates product ownership and installs RAM read and Playbook
read/propose grants. It does
not check the model or live worker connectivity. Set `worker.enabled: true` in
`playbook-extraction-values.yaml` and apply it:

```bash
helm upgrade playbook playbook/helm --namespace redis-ai \
  -f playbook-values.yaml -f playbook-extraction-values.yaml
kubectl --namespace redis-ai rollout status \
  deployment/playbook-redis-agent-playbook-worker
```

Check worker readiness, `/metrics`, configured model/target access, and monitoring
described in the [operations runbook](../../docs/runbooks/playbook-extraction-operations.md).
GET the binding again for its latest version, then activate it:

```bash
jq '{expectedVersion:.version,enabled:true}' binding.json > activation.json
curl --fail-with-body -sS -X PATCH \
  "$PLAYBOOK_CP_URL/v1/playbooks/$PLAYBOOK_ID/extraction/bindings/$BINDING_ID" \
  -H "Authorization: Bearer $PLAYBOOK_ADMIN" -H 'Content-Type: application/json' \
  --data-binary @activation.json --output binding.json
```

On a version conflict, GET again and rebuild `activation.json`. Send a small,
representative session to the bound RAM store and let it become idle under the
binding policy (30 minutes by default; `job.idleWindowSeconds` accepts 60–86400).
Discovery uses the five-minute binding cadence, not an immediate
manual-run API. Inspect the Playbook DP proposal inventory and supporting evidence
using an independent inspection credential. A healthy stack may produce no proposal for a session with
no usable FAQ; use a known FAQ sample for the initial canary. An accepted proposal
still requires human review and publication before it becomes published knowledge.

Keep the initial deployment at one replica and one extraction consumer. The
[post-merge qualification plan](../../docs/runbooks/playbook-extraction-operations.md#agreed-post-merge-work)
defers real-model sample-data quality assessment and scale/load qualification to
the next sprint; a successful installation does not establish those results.
For pause, cleanup and credential retirement, follow the
[binding lifecycle instructions](#operator-flow-for-the-bindings-api).

## FIPS-oriented profile

Set `security.profile=fips` only when the images were built with the Go FIPS
module and all dependency transport is ready:

```yaml
security:
  profile: fips
dataplane:
  identityServiceBaseURL: https://identity.internal.example
tls:
  caCertSecret: redis-ai-private-ca
```

The chart sets `GODEBUG=fips140=on` in every container. FIPS renders fail unless
`dataplane.identityServiceBaseURL` (and any extraction Identity Service
override) is an explicit HTTPS endpoint, and refuse
`identityService.allowInsecureTransport`. Set the Identity Service release's
own profile and its HTTPS grant-validator URL there (see
[FIPS and TLS trust](#fips-and-tls-trust)). The storage overlay must use
`rediss://`; CP and DP validate that at startup. The optional CA
Secret is mounted at `/etc/ssl/custom` in every process.

This is a FIPS-oriented operating profile, not by itself a compliance claim.
The workloads still listen on HTTP; the chart does not provision TLS termination
or a mesh. Supplying HTTPS URLs alone does not create secure service endpoints.

## Images and upgrades

### Embedding configuration migration

Legacy `inference.models[].client` configuration is rejected by Playbook DP.
Keep only `provider`, `model` and `dimensions` in the model catalog, and move
private client endpoints/credentials into `embedders_connection_details` in the
DP inference Secret, keyed by the catalog's provider. See the
[inference Secret example](#prerequisites). Both CP and DP now reject obsolete
model fields; check both workloads' readiness and logs after upgrading.
This changes connection configuration, not
the vector space: preserve the existing provider/model/dimensions identity.

### Image and Secret rollouts

From the repository root, `task playbook:build:docker` builds development
license targets when `LICENSE_PUBLIC_KEY_B64` is absent. Supplying that BuildKit
secret builds the production `release` targets, which refuse to start without
an embedded license verifier key. Runtime configuration is always mounted; no
configuration or customer secret is baked into an image.

Roll forward and backward with immutable image tags. Redis records and indexes
are external to the release, and the first release has no prototype-data
migration. After rotating a mounted credential or storage Secret, update its
`existingSecretChecksum` and run `helm upgrade`; if no checksum is managed,
restart the affected Deployment so startup validation and long-lived
dependencies are re-established against the new material.

Run the package gates with:

```bash
task playbook:test:chart
task playbook:fips:test:runtime
task playbook:test:lifecycle
task playbook:test:release-artifacts
```

Manual dispatch of the package-validation workflow accepts a Playbook version
(for example, `0.1.0-alpha1`). Dispatching it without a version instead uses
`0.0.0-dev.sha<commit-prefix>`. Either path creates a seven-day Actions artifact containing production
image archives, the stamped chart, per-image SBOMs, the public and internal
OpenAPI contracts, a machine-readable component manifest, an image-values
overlay, and SHA-256 checksums. The gate verifies license
enforcement, the Go FIPS build posture, forbidden module absence, and fixed
high/critical image vulnerabilities.

The separate release-artifact CI gate uses ephemeral issuers to test missing,
wrong-product, and valid licenses, verifier-key rotation with fixed build
metadata, and rejection of development binaries. Package validation also installs
the exact chart archive and production images on KinD, using a one-day Playbook
license signed with the existing `LICENSE_PRIVATE_KEY` and verified by the
embedded `LICENSE_PUBLIC_KEY_B64`. Key and license files are temporary and never
enter artifacts. The KinD smoke test checks
generated credential reuse across an upgrade and workload restart, then exercises
the service lifecycle. These checks do not establish EKS, real-provider, TLS,
backup/restore, or cross-version upgrade qualification.

The validation bundle targets `linux/amd64`; each component's OS,
architecture, config digest (`imageId`), frozen registry manifest digest, and versioned reference are recorded in
`manifest.json`. The chart records intended public image names; the overlay
selects the local names inside the unpublished archives. After verifying
`SHA256SUMS`, load the images into the Kubernetes nodes and apply the overlay
after your deployment values. For KinD, load into Docker and then into the
default `kind` cluster (adjust its name if needed):

```bash
gzip -dc images/oci-playbook-cp-onprem.tar.gz | docker load
gzip -dc images/oci-playbook-dp.tar.gz | docker load
kind load docker-image --name kind \
  playbook-controlplane-onprem:0.1.0-alpha1 \
  playbook-dataplane-onprem:0.1.0-alpha1
helm upgrade --install playbook chart/redis-agent-playbook-0.1.0-alpha1.tgz \
  --namespace redis-ai --create-namespace \
  -f deployment-values.yaml \
  -f playbook-images.values.json
```

Package validation does not push an image or chart or create a GitHub release.
For a safe branch smoke, dispatch only the package workflow with the version
input blank:

```bash
gh workflow run playbook-onprem-package.yml --ref <fix-branch>
```

This uses a synthetic `0.0.0-dev.sha<commit-prefix>` version and temporary Actions
artifacts; it does not reserve public versions or open an Enterprise Helm PR.
Packaging hashes the config bytes in each saved image and compares them with
the frozen registry manifest, independent of Docker's classic/containerd `.Id`
semantics. It also runs the publication integrity guard offline for CP and DP before uploading the bundle. To repeat that read-only guard
against a downloaded bundle:

```bash
node playbook/tools/release/publication.js verify --bundle <bundle-directory>
```

After the desired source is merged to `main`, dispatch the Playbook on-prem
release workflow with the Playbook version. It runs the same validation,
publishes the two Docker Hub image tags, and opens an
Enterprise Helm PR containing the stamped chart under `ai/charts/redis-agent-playbook`
and its `release-redis-agent-playbook.yaml` workflow. A Helm maintainer reviews and
merges that PR. Dispatch the chart workflow from Helm `master` to publish the
chart to `https://helm.redis.io/ai`. The Iris CI GitHub App must have Contents,
Pull requests, and Workflows write access to the Helm repository; the release
workflow checks that grant before pushing any images.

Iris requires no Git tag or GitHub Release. As with Agent Memory, the public
Helm repository's shared chart publisher creates its own chart tag and GitHub
Release to host the archive and updates the public Helm index.

The public chart name is `redis-agent-playbook`, matching Redis Agent Memory's
chart naming. After the first release under this name, install it with
`helm upgrade --install playbook redis-ai/redis-agent-playbook --version <version>`
and the deployment values described above. The previously published
`0.1.0-alpha.2` chart remains in the index for existing users. The renamed chart
is a separate Helm chart identity; its default resource names and selector
labels change with the chart name. Existing installations need a migration
plan before switching to this chart.

### Publication and recovery

The release workflow serializes publication with RAM under the
shared `iris-onprem-release-publication` group. It builds and publishes no
Identity Service image; operators install a published `iris-identity-service`
release. Each image job records its registry
manifest digest and can be retried independently. Existing tags are accepted only
when their digest equals the frozen candidate; mismatches and registry errors
stop publication. After a partial failure, use **Re-run failed jobs** on the
original run within the candidate artifact's seven-day retention window. A fresh
build can differ because it embeds build timestamps; use a new version if its
digest differs from an already published tag.

The Enterprise Helm PR records both digest-qualified image references,
the source commit/run, and the exact tested chart checksum in
`ai/releases/redis-agent-playbook/<version>.json`. Its chart comes directly from the
validated candidate archive, including templates and vendored dependencies.
The candidate and per-image publication records remain available as workflow
artifacts for retries within their retention windows. No Iris GitHub Release or
manual Git tag is part of this handoff.
## Extraction worker

The existing data-plane image also runs `--mode worker`. Enable the separate worker
Deployment with `worker.enabled=true`; the default is false. Its HTTP service
exposes `/health/liveness`, `/health/readiness`, `/build-info` and `/metrics`, with no
business or demo routes. It uses the same shared on-prem runtime as RAM.

1. Provision regional queue Redis with persistence, `noeviction` and capacity
   monitoring. Keep metadata Redis and content Redis separate. Queue eviction
   compatibility is advisory at startup, as in RAM; an unreadable configuration
   does not prove durability. Align one active regional deployment's producers,
   consumers and source deployment. Multiple replicas within that region are supported;
   two regions must not dispatch the same binding inventory.
2. Set `worker.region` and
   either `extraction.connection.ramControlPlaneBaseURL` (live store discovery) or
   optional `extraction.sources` (tenant-scoped store suggestions). `worker.targetURL` defaults
   to the release's DP service. Set an HTTPS endpoint when the security profile
   requires it. Enable `extraction.connection` using the RAM connection settings
   above. Set `worker.sourceURL` to the RAM data-plane endpoint. The chart gives
   the worker its own ServiceAccount
   (`<fullname>-worker`), projects separate `api://memory-dp` and `api://playbook-dp` tokens, and adds that subject to
   the CP's grant list. Configure RAM's `auth.service_subjects.subjects` to accept
   the worker subject. `worker.sourceTokenAudience` defaults to `api://memory-dp`
   and must match RAM's accepted audience; `worker.sourceTokenExpirationSeconds`
   defaults to 3600. The CP calls IdS Control with its own ServiceAccount JWT; it
   has no RAM data-plane token or endpoint.
   Store suggestions, live or configured, do not approve source access. Set
   either `ramControlPlaneBaseURL` or `extraction.sources`, not both. For live
   discovery, RAM's control plane must trust the
   control-plane subject in its `auth.workload_identity`, with the audience
   `ramControlPlaneAudience`, the tenant `tenantId`, and `roles: [viewer]`.
3. Create `worker.existingSecret` with the following **shape**, substituting real
   values privately. The mounted overlay is merged after the chart's public config
   and storage overlay; keep credentials out of Helm values and CLI arguments.

   ```yaml
   inference_providers:
     private-model:
       protocol: openai
       endpoint:
         base_url: https://your-inference-service.example/v1
         generation_api: chat_completions
       http_client:
         timeout: 30s
         max_retry_attempts: 0
   worker:
     redis:
       urls: [rediss://USER:PASSWORD@regional-queue:6379]
     llm:
       provider: private-model
       models:
         default_chat_model: gpt-5.6-luna
       reasoning_mappings:
         - model_patterns: [gpt-5.6-luna]
           values:
             low: {reasoning_effort: low}
       credentials:
         type: static
         api_key: REPLACE_WITH_MODEL_CREDENTIAL
   ```

4. Install/upgrade with `worker.enabled=true`, `extraction.enabled=true`, and
   `extraction.connection.enabled=true`; keep individual bindings disabled
   until probes and `/metrics` are healthy. A BYO CP config must explicitly carry
   the matching `extraction` block; the chart cannot override that external Secret.
   Startup fails for missing source/model/region/token-file settings or unreachable Redis.
5. Create a binding, wait for authenticated preparation to mark it ready, then
   enable it and let
   the dispatcher discover it. A binding uses the documented five-minute cadence;
   `worker.dispatchInterval` only controls polling of due bindings. Pausing a
   binding or disabling the deployment gate stops subsequent reads/mutations.
6. Configure metrics scraping and the existing OTel collector using
   `worker.opentelemetry`. Alert on sustained queue age, permanent failures,
   exhausted attempts, lease loss, provider errors and dispatch failure/staleness.
   Example Prometheus signals: `jobqueue_oldest_pending_seconds`,
   `jobqueue_processing_duration_seconds_count{processing_outcome="permanent_failure"}`,
   `playbook_extraction_runs_total{exhausted="true"}`,
   `playbook_extraction_dispatch_last_success_age_seconds`. Per-pod gauges describe
   the same regional queue; use `max`, not a sum of replicated depth snapshots.
   `jobqueue_delivery_age_seconds` measures age since submission on every
   delivery, including retries and scan continuations. Use oldest-pending age
   for backlog alerts; delivery age is not distinct-job first-pickup latency.
7. Before production enablement, rehearse worker kill/restart, regional Redis
   failover, metadata recovery, gate pause/resume and provider throttling under
   expected traffic. Confirm model budget/capacity using measured usage. There is
   no fleet-wide quota or fairness guarantee in this release.

The extraction and consolidation selection is `gpt-5.6-luna` with low reasoning
effort, matching [the research implementation](https://github.com/redislabsdev/ai-research-semantic-cache/tree/main/experiments/faq-extraction).
Set a provider endpoint that serves that model. Model access is deployment configuration;
the deterministic qualification fixture does not require a live model account.
Include the explicit reasoning mapping above: the shared inference library's
built-in model list does not yet map this model, so a model name alone would omit
the requested effort on the wire.

The LLM shape follows RAM's `inference_providers` connection registry and strategy
`llm` block. A provider key may be an alias with `protocol: openai`; it identifies
the wire protocol, not the hosting company. The block accepts `credentials`,
`models`, `reasoning_mappings`, `error_handling`, and per-field `http_client`
overrides. Explicit `max_retry_attempts: 0` overrides a provider's retry setting.
The example disables shared HTTP transport retries; the pinned OpenAI SDK still
defaults to two retries. A separate shared-inference follow-up will consolidate
retry ownership; count actual HTTP attempts during capacity qualification.
FAQ extraction requests JSON through prompts, validates it locally, and sets
`max_completion_tokens`. Both `generation_api: responses` and
`generation_api: chat_completions` work through the shared inference client. See
the [extraction ADR](../../docs/adr/MOD-18196-playbook-memory-extraction.md)
for the decision contract.

Deployment tuning uses `worker.timeout` (Helm `worker.timeout`, strategy default 2m),
`worker.reasoning_effort` (`worker.reasoningEffort`, default low),
`worker.max_input_tokens` (`worker.maxInputTokens`, default 8192), and
`worker.max_completion_tokens` (`worker.maxCompletionTokens`, default 4096).
Both token limits must remain positive; startup rejects an input cap too small
to fit the fixed FAQ prompts. An empty reasoning effort uses the provider
default; mappings translate semantic effort for a particular model.
The input cap counts serialized prompt overhead using the reference tokenizer,
not each provider's exact tokenizer. A complete RAM rolling summary, when present,
is followed by the largest earliest whole-event prefix that fits. These settings
serve both extraction and consolidation across all bindings; bindings do not
select model budgets. Models and credentials are never selected by a
binding or inherited from RAM. Worker inference credentials remain independent of
RAM service identity, Playbook access credentials, and DP embedding credentials.

Secret contents are loaded at client construction: update the appropriate `existingSecretChecksum` and run
`helm upgrade`, or restart the affected workload after changing a Secret in place.
Model changes apply to unfinished/new sessions; retained completed sessions do not
re-extract automatically.

`worker.jobs` selects registered job types; concurrency is per queue per replica.
Workers stop dispatch, stop every consumer, drain, then close dependencies. The
chart requires termination grace of at least consumer drain plus 60 seconds;
90 seconds covers the default 30-second drain. A forced kill can replay an entire
session; proposal creation may duplicate after an uncertain response, as already
accepted in the ADR. Do not delete ledger keys to make a rollout look fresh.

Four charged failures exhaust a session's durable allowance. Restore the dependency
before deliberately recovering a selected session with the packaged
`extraction-status` / `extraction-recover` modes. An empty queue is not proof of
corpus completion. The [operations runbook](../../docs/runbooks/playbook-extraction-operations.md)
owns status/recovery commands, monitoring signals, read-only queue inspection
and alert guidance. A long pause/outage can expire the ledger's 30-day refresh TTL.

Session state uses the bounded hash ledger; unexpected persisted types fail
without rewriting them. Regional queues use `playbook-extraction:<region>:scan|extract`.

The production profile requires `worker.source_token_file`; the chart
supplies this path and its projected volume automatically. Cluster token rotation
and grant revocation can be checked locally; Neptune issuer routing remains
environment-specific rollout work. The automated real-service test is documented
in the [pipeline evaluation](../README.md#evaluate-the-connected-extraction-pipeline-locally).
There is no public reset or manual-run HTTP API.

The shared `tracing.enabled` and `tracing.otlpGRPCEndpoint` values also configure
and roll the extraction worker. When the shared switch is off,
`worker.opentelemetry` keeps its existing overrides; when enabled, the shared
switch and endpoint take precedence. `tracing.capture` applies only to DP serving
traces and does not roll the worker. Scrape each worker pod on port 9203 for the
existing extraction, queue, and inference metrics. Worker source/target calls
propagate W3C trace context without baggage. Management API metrics cover the
Settings UI's extraction bindings and the control-plane clear action; these
management calls never capture response content.
